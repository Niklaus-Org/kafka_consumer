The Problem Statement

Traditional video streaming platforms struggle with real-time analytics at scale. Current REST-based polling approaches create massive network overhead, high latency (5-10 second delays), and database bottlenecks when tracking millions of concurrent viewer events (play, pause, seek, quality changes). Systems cannot handle 10,000+ events per second without degrading user experience. Aggregating analytics requires post-processing delays, making dashboards stale. Complex event correlation and pattern detection become computationally expensive. There's no efficient way to stream, process, and persist real-time viewer engagement metrics without building a complete custom solution from scratch.

✅

The Solution Architecture

Build an event-driven, real-time analytics pipeline using Apache Kafka as the event backbone. Frontend captures user interactions (play, pause, seek, quality changes) and sends them via REST to a Spring Boot producer, which publishes events to Kafka topics partitioned by videoId. Kafka Consumer services listen to these topics, deserialize events in real-time, process aggregations (views, watch time, play-pause ratios), and persist metrics to PostgreSQL. React frontend polls analytics endpoints every 2 seconds, displaying live dashboards with charts. This decouples event capture from analytics processing, handles 10K+ events/sec, provides sub-second latency, enables horizontal scaling via consumer groups, and ensures fault tolerance. Advanced features include WebSocket push updates, idempotent processing, audit logging, and comprehensive monitoring.

🎯 Problems vs Kafka Solutions

❌

REST Polling Bottleneck

Problem: Frontend polls every 2 seconds for updates. With 1M users, that's 500K requests/sec just for polling!

Kafka Solution: Bi-directional push via consumer groups. Each consumer processes events once, scales horizontally. Same 1M users = only 10K events/sec to process.

Impact: 50x reduction in network calls
❌

Database Bottleneck

Problem: Every analytics request hits database directly. 100K concurrent queries crash the DB. Response time: 500ms-5sec.

Kafka Solution: Consumer aggregates & caches in DB. Frontend queries pre-aggregated metrics from analytics table (indexed). Response time: <5ms. Database handles 10x more load.

Impact: 100-1000x faster queries
❌

Latency Issues

Problem: 2-5 second delay before analytics update. User plays video but dashboard shows old data. Poor UX.

Kafka Solution: Events processed in real-time by consumers. Analytics update in <500ms. With WebSocket (Phase 10): <100ms push latency.

Impact: 10-50x faster insights
❌

Lost Events

Problem: No event queue. During peak hours, REST requests get dropped. 5-10% event loss. Metrics incomplete.

Kafka Solution: Kafka acts as event buffer. 7-day retention. Consumer fails? Restart and replay. Zero event loss. Exactly-once semantics guarantee.

Impact: 100% reliability
❌

Scaling Nightmare

Problem: Cannot scale without monolithic changes. One server handles 1K events/sec max. Need 10 servers for 10K events/sec = complex deployment.

Kafka Solution: Add consumer instances = instant scale. 1 consumer → 5 consumers → 50 consumers. Kafka auto-distributes partitions. Linear scaling.

Impact: Infinite horizontal scale
❌

Data Silos

Problem: Analytics locked in one service. Data science team wants raw events for ML. Reporting team wants aggregations. Incompatible.

Kafka Solution: One topic, many consumers. Analytics consumer → dashboard. ML consumer → model training. Reporting consumer → data warehouse. Decoupled pipelines.

Impact: Universal data source

How Kafka Achieves This Scale

📂

Partitioning

Topic "video-events" split into 300 partitions (one per 3,300 events/sec). Each partition processes independently.

👥

Consumer Groups

Add new consumer instance → Kafka auto-assigns partitions to it. Remove instance → Kafka redistributes load. Dynamic scaling.

💾

Log-Based Storage

Append-only log structure. Write: O(1) sequential I/O. Read: O(1) with offset. Massively parallel without locks.

🔄

Replication

Each partition replicated across 3 brokers. One fails → others serve traffic. Zero downtime. High availability.

⚡

Batching

Producers batch 1000s of events into single write. Consumers batch process. 10-100x throughput improvement.

🗜️

Compression

Snappy/LZ4 compression reduces network & storage by 5-10x. Same events, fraction of bandwidth.

🔐 How System Identifies & Tracks Individual Users

The system uses a unique userId attached to every event. This "golden thread" runs through the entire architecture, ensuring each user's actions are tracked individually while allowing aggregated metrics across all users.

📊 How Data Is Stored (Two Different Tables)

📋 video_events Table (Per-User Audit Trail)

Stores EVERY event from EVERY user. Keeps userId so you know who did what.

id videoId userId eventType timestamp
1 abc123 alice-550e8400 PLAY 12:00:00
2 abc123 bob-774ba920 PLAY 12:00:02
3 abc123 alice-550e8400 PAUSE 12:00:10
4 abc123 bob-774ba920 SEEK 12:00:15

✅ Can query by userId to get one user's history

📈 video_analytics Table (Aggregated Metrics)

Stores aggregated metrics across ALL users. userId is NOT stored here.

videoId total_views play_count pause_count avg_watch_time
abc123 2 3 2 67.5s

✅ Same for all users (no userId column)

🎯 Why Two Tables?

  • video_events: Keep detailed history for each user, compliance, ML training
  • video_analytics: Quick metrics queries for dashboards (aggregated, faster)

🔍 Example Queries: How userId Enables Different Queries

❌ Get Only Alice's Events

SELECT * FROM video_events WHERE videoId = 'abc123' AND userId = 'alice-550e8400' ORDER BY timestamp; Result: Events 1, 3 (Alice's PLAY, PAUSE)

Use: Show Alice her personal watch history

❌ Get Only Bob's Events

SELECT * FROM video_events WHERE videoId = 'abc123' AND userId = 'bob-774ba920' ORDER BY timestamp; Result: Events 2, 4 (Bob's PLAY, SEEK)

Use: Show Bob his personal watch history

✅ Get All Events for Video

SELECT * FROM video_events WHERE videoId = 'abc123' ORDER BY timestamp; Result: Events 1, 2, 3, 4 (all users)

Use: Audit trail for compliance/debugging

✅ Get Aggregated Metrics

SELECT * FROM video_analytics WHERE videoId = 'abc123'; Result: total_views=2, play_count=3 (userId is NOT in results)

Use: Show dashboard metrics (same for all users)

❌ Count Events by User

SELECT userId, COUNT(*) as event_count FROM video_events WHERE videoId = 'abc123' GROUP BY userId; Result: - alice-550e8400: 2 events - bob-774ba920: 2 events

Use: Understand per-user engagement

❌ Find Pause Points (All Users)

SELECT userId, timestamp, watchedSeconds FROM video_events WHERE videoId = 'abc123' AND eventType = 'PAUSE'; Result: Where did users pause? (shows per-user behavior)

Use: Identify hard sections in video

🌟 Why userId Is Crucial (The "Golden Thread")

📊 Analytics

Aggregate metrics from all users. Total views = sum of all plays from all userIds

👤 User Experience

Show each user their personal history and recommendations based on their userId

🔍 Debugging

If a user reports issue, query by userId to see exactly what they did

🤖 Machine Learning

Train recommendation engines using per-user patterns from userId tracking

📋 Compliance

Audit trail with userId ensures you know exactly who did what (GDPR, etc.)

🎯 Personalization

userId enables personalized experiences: "You paused at 5 min, need help?"

✨ Final Clarity: Why Both See "Total Views: 2"

Alice's Dashboard:
She sees "Total Views: 2" because the backend queries video_analytics table (NO userId filter). This returns aggregated count from ALL users who watched.


Bob's Dashboard:
He also sees "Total Views: 2" - same query, same table, same result. Both are shown platform-wide metrics, not personal metrics.


Behind The Scenes:
Individual events ARE tracked with userId in video_events table. But when displaying "Total Views", the dashboard queries video_analytics which has already aggregated all user events into one metric. The userId identification enables the aggregation to work correctly!
